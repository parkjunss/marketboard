# MarketBoard — 투자 기능 세부 설계

> 작성: 2026-07-22
> `INVESTING_FEATURE_IDEAS.md`의 19개 항목에 대한 세부 설계. **코드 없음** — 데이터 흐름/저장 전략/성능·부하/안정성만.
> 이번 세션에서 확립된 패턴을 최대한 재사용: (a) 소수·고정 개수 대상(섹터 11개, SPY)은 **스케줄 재계산 + MySQL 스냅샷 + Redis 캐시**, (b) 임의 티커(개별 종목)는 **요청 시 지연 계산 + TTL 기반 MySQL 캐시 + 실패 시 이전 데이터 유지**, (c) N개 심볼을 다루는 배치는 **벌크 쿼리 1회**(이번 세션에 인디케이터/시장폭에서 이미 증명: 506개 심볼 벌크 처리 18ms), (d) 외부 API 호출은 절대 요청 스레드에서 직접 블로킹하지 않음.

## 바로 해볼 만한 것

### 1. 감마 익스포저(GEX)
**데이터 흐름**: 신규 외부 호출 없음. `options_levels.py`가 CBOE 응답에서 이미 파싱하는 계약별 `delta`/`gamma`를 지금은 버리고 있는데, strike별로 `gamma × open_interest × 100`(콜은 +, 풋은 -)을 합산하면 순 감마 익스포저, 이게 0을 지나는 strike가 "감마 플립" 지점.
**저장**: 신규 테이블 불필요 — 기존 `options_levels_snapshot`의 `payload_json`에 `netGex`, `gammaFlipStrike` 필드만 추가.
**성능/부하**: 이미 파싱된 배열 위에서 O(n) 합산 1회 추가되는 것뿐 — 응답시간 사실상 무변화(1s 미스/50ms 히트 그대로).
**안정성**: 새 실패 지점 없음(기존 CBOE 호출 실패 케이스 그대로 상속). 다만 **부호 컨벤션 검증 필요** — CBOE 델타/감마가 매수자 관점인지 매도자(딜러) 관점인지에 따라 부호가 뒤집힐 수 있어서, SPY처럼 이미 알려진 GEX 값이 있는 종목으로 검증 후 배포해야 함(수치는 맞는데 부호가 반대인 채로 나가면 "지지"라고 보여준 게 실제론 "저항"이 되는 조용한 오류).

### 2. 52주 신고가/신저가 종목 리스트
**데이터 흐름**: `MarketBreadthService.recompute()`가 이미 심볼별로 신고가/신저가 여부를 판정하고 카운트만 남기고 버림 — 같은 루프에서 티커를 리스트에 같이 모으기만 하면 신규 DB 조회 없음(이번 세션에 만든 벌크 fetch 재사용).
**저장**: `MarketBreadthSnapshot`에 필드 추가보다는 별도 소테이블(예: 스냅샷 날짜당 티커+구분 행)을 두는 편이 나중에 "S&P500만" 같은 필터링에 유리.
**성능/부하**: 배치 잡(1일 1회) 안에서 끝나는 추가 쓰기 — 하루 수십 건 수준, 부하 영향 없음.
**안정성**: 카운트 계산과 티커 리스트 수집이 **같은 트랜잭션 안에서 같은 루프 결과로** 나와야 함 — 따로 계산하면 둘이 불일치할 위험(예: 카운트는 5인데 리스트는 4개).

### 3. 관심종목 vs 지수 상대강도 차트
**데이터 흐름**: `price_history`(종목)와 `market_index_history_snapshot`(지수) 둘 다 이미 DB에 있음, 신규 외부 호출 없음. 기간 시작일=100 기준으로 정규화해서 겹쳐 그리기만.
**저장**: 캐싱 불필요 — 사용자별 워치리스트+임의 기간 조합이라 캐시 적중률이 낮고, 기반 쿼리 자체가 이미 인덱스 스캔이라 저렴함(이번 세션에 `price_history` 풀스캔 버그를 고쳐서 `(symbol_id, timeframe, ts)` 인덱스를 타게 해둔 상태).
**성능/부하**: 워치리스트 크기가 자연히 작음(사용자가 직접 담은 것) — 그래도 종목별 개별 쿼리 대신 **IN절 벌크 쿼리 1번**으로(이번 세션 `PortfolioService.resolvePrices()`와 동일 패턴). N+1 걱정 없음.
**안정성**: 순수 내부 DB 읽기라 새 실패 지점 없음. 지수 데이터가 아직 스냅샷 안 된 슬러그를 고르면 404 — 프론트가 해당 지수만 빼고 나머지는 그리도록 처리.

### 4. Put/Call·옵션레벨 스냅샷 이력 적재
**이게 이번 4개 중 부하 설계가 제일 중요한 항목** — "매 요청마다 새 행 추가"는 절대 금지. 지금처럼 `(ticker)` 유니크가 아니라 **`(ticker, snapshot_date)` 유니크**로 바꿔서, "하루 첫 요청은 새 행 삽입, 같은 날 이후 요청은 그 행을 갱신"하는 방식(이미 `MarketBreadthSnapshot`이 날짜 기준으로 쓰고 있는 바로 그 패턴)을 개별 종목 스냅샷에도 그대로 적용.
**왜 중요한가**: SPY는 10분마다 스케줄 갱신이라 그냥 매번 새 행을 쌓아도 하루 144행으로 예측 가능하지만, 개별 종목은 **사용자 트래픽에 따라 갱신 빈도가 들쭉날쭉**이라(인기 종목은 자주, 안 보는 종목은 거의 안 됨) 매 갱신마다 새 행이면 성장 속도를 예측할 수 없음. 날짜당 1행으로 묶으면 "티커 수 × 최대 하루 1행"으로 상한이 명확해짐.
**성능/부하**: 위 설계로 가면 쓰기 부하 증가는 무시할 만한 수준. "최신값" 조회는 기존과 동일(날짜 내림차순 top 1), "이력" 조회만 날짜 범위 쿼리로 신규 추가.
**안정성**: 과거 이력이 생기므로 오래된 행 정리(retention) 정책도 같이 정해야 함 — 예: 90일 지난 행은 별도 배치로 삭제, 안 하면 시간이 지날수록 무한정 늘어남.

## 기술적 분석 확장

### 5. MACD / 볼린저 밴드 / Stochastic
**핵심 설계 분기점**: 이 지표들을 "차트에 겹쳐 그리는 오버레이"로 쓸 거면 **서버에 저장할 필요가 없음** — 현재 SMA 오버레이가 이미 클라이언트가 화면에 로드한 캔들 데이터로 프론트에서 직접 계산하는 방식(`CandleChart`의 `computeSma`)이고, MACD/볼린저/Stochastic도 캔들 배열만 있으면 계산 가능한 순수 함수라 똑같이 갈 수 있음. 이 경우 백엔드 변경 자체가 없고 부하도 0.
서버 계산이 필요한 건 "현재 MACD 값으로 스크리닝하고 싶다"거나 "MACD 골든크로스로 알림 걸고 싶다"는 경우뿐(7번·13번과 연결) — 그때는 `TechnicalIndicators.java`에 순수함수 추가 + `IndicatorType` enum 확장 + 기존 5분 스케줄 잡이 같이 계산.
**성능/부하**: 오버레이 방식이면 무(無). 스캔/알림용 서버 계산이면 이번 세션에 이미 벌크 최적화된 `IndicatorCalculationService`에 얹는 것뿐이라 506개 심볼 기준 몇 ms 추가 수준.
**안정성**: 순수 계산 함수라 외부 의존성 없음, 새 실패 지점 없음.

### 6. 거래량 지표: OBV·VWAP·MFI
OBV는 5번과 동일하게 오버레이면 클라이언트 계산이 정답. **VWAP은 주의가 필요**: 하루 단위로 리셋되는 분봉 기반 지표라 분봉(`timeframe='1m'`)이 있어야 하는데, 지금 분봉은 실시간 추적 중인 13~50개 종목만 있고 S&P500 나머지 450여 개는 일봉만 있음 — VWAP은 사실상 실시간 추적 종목 한정 기능이 됨(스코프 명시 필요).
MFI는 스캐너용(16번)으로 서버 계산 — 5번과 같은 스케줄 잡 확장 패턴.
**성능/부하**: 5번과 동일한 논리.
**안정성**: VWAP의 경우 분봉 데이터가 없는 종목에 대한 요청은 "지원 안 됨"을 명확히 반환(빈 배열이나 0 대신).

### 7. 골든크로스/데드크로스 알림
**설계**: 이번 세션에 벌크 최적화한 `IndicatorCalculationService`가 각 심볼의 **기존 SMA20/50 값을 이미 메모리에 갖고 있는 상태**(교체 전 조회한 맵)에서 새로 계산한 값과 비교만 하면 교차 감지 가능 — 신규 쿼리 전혀 불필요, 5분 배치 안에서 비교 연산 하나 추가되는 수준.
**전달 방식**: 완전히 새로운 알림 인프라를 만들기보다 **기존 `alerts` 테이블/Redis 미러/STOMP 푸시 구조를 재사용** — `AlertCondition`에 `GOLDEN_CROSS`/`DEATH_CROSS`를 새 조건으로 추가하면, 이미 검증된 저장→미러→트리거→푸시 파이프라인을 그대로 탐. 사용자가 "이 종목 골든크로스 알림"을 명시적으로 등록하는 옵트인 방식.
**성능/부하**: 기존 5분 주기 배치에 얹히므로 별도 스케줄/부하 없음.
**안정성**: 최악의 경우 감지가 한 틱(5분) 늦는 정도 — 가격 알림과 동일한 신뢰성 수준.

### 8. 가격 기반 지지/저항(스윙 고점/저점)
**데이터 흐름**: 화면에 이미 로드된 캔들 배열에서 지역 고점/저점(예: 앞뒤 N개 봉보다 높은/낮은 봉)을 찾는 순수 함수 — 클라이언트 계산, 신규 백엔드 없음. 8번(옵션 기반)과 상호보완적 신호라 같은 차트에 다른 색으로 겹쳐도 됨.
**성능/부하**: O(n) 1회 패스, 무시할 수준.
**안정성**: 새 실패 지점 없음.

## 포트폴리오 리스크/분석

### 9. 포트폴리오 베타 / 10. 섹터 배분
**데이터 흐름**: `symbol_profiles.beta`/`.sector`는 이미 24시간 TTL로 캐시돼 있지만 **티커별 지연 조회 방식**이라, 포트폴리오 포지션 N개에 대해 그대로 쓰면 N+1 쿼리가 남. 이번 세션에 `QuoteService.resolvePrices()`를 만들며 썼던 벌크 조회 패턴(`findByTickerIn`)을 `SymbolProfileService`에도 추가해서 포트폴리오 조회 시 한 번의 IN절 쿼리로 전부 가져와야 함.
**성능/부하**: 벌크 조회 적용 시 포지션 10~30개 기준 DB 읽기 1회, 50ms 이내 예상. 베타/섹터 데이터 없는 신규 상장 종목은 계산에서 제외하고 "N개 중 M개만 반영"을 명시.
**안정성**: `symbol_profiles`가 아직 캐시 안 된 종목(한 번도 상세페이지 방문 안 한 종목)은 null — 이 경우 라이브 조회로 즉시 채우진 말고(포트폴리오 조회가 매번 yfinance 호출을 기다리게 됨) 다음 배치나 다음 상세페이지 방문 때 채워지도록 두고, 응답에는 "제외됨" 표시만.

### 11. 리스크 지표: 변동성·MDD·샤프비율
**데이터 흐름**: `price_history` 벌크 조회로 일별 수익률 시계열 구성 → 표준편차(변동성)/누적 최고점 대비 낙폭(MDD)/샤프비율 계산. 이미 `collector/app/backtest.py`가 pandas로 정확히 이 종류의 계산(수익률, 낙폭)을 하고 있어서, **Java가 아니라 Python collector 쪽에 확장하는 게 기존 아키텍처 분업(자바=조회/서빙, 파이썬=수치계산)에 맞음**.
**성능/부하**: 포트폴리오 구성은 자주 안 바뀌므로 매 조회마다 재계산해도 되는 수준(온디맨드, 별도 캐시 불필요) — 다만 5년치 일봉 × 포지션 20개처럼 큰 조합에서 체감 지연이 생기면 그때 캐싱 고려.
**안정성**: 보유 기간이 짧은(최근 편입) 종목은 계산에 필요한 최소 이력이 부족할 수 있음 — 해당 종목만 제외하고 계산하되 "일부 종목 제외됨" 명시.

### 12. 거래 이력 기반 실현손익 추적 — 가장 큰 항목
**전제**: `UPGRADE_IDEAS.md`에 이미 "선행 과제"로 적혀있듯, 지금 `portfolio_positions`는 수량/평단가 **스냅샷**이라 매매 기록 자체가 없음. 이 항목은 다른 포트폴리오 기능(실현손익, 배당 기록, 보유기간별 수익률)의 기반이라 먼저 결정할 게 많음.
**설계가 필요한 결정 사항**(구현 전에 먼저 정해야 함):
- **원장 테이블**: 매수/매도 각각을 append-only(추가만, 수정/삭제 없음)로 기록하는 거래 테이블 신설 — 회계 원장처럼 불변으로 유지해야 나중에 감사/재계산이 안전함.
- **평단가 계산 방식**: FIFO(선입선출, 세무상 표준에 가까움) vs 이동평균(계산 단순) — 둘 중 하나를 명시적으로 정해야 실현손익 숫자가 나옴. 이건 구현 방식이 아니라 **투자 계산 방법론 결정**이라 사용자 확인이 필요한 지점.
- **기존 데이터 이관**: 지금 있는 스냅샷(수량/평단가)엔 매매 이력이 없으므로, 마이그레이션 시 "기초 잔고"라는 가상의 거래 1건으로 시딩해야 기존 포지션이 안 깨짐.
- **읽기 성능**: 매번 전체 거래 이력을 순회해서 현재 잔고를 계산하면 느려질 수 있으니, `portfolio_positions`를 "거래 원장에서 파생된 현재 상태 캐시"로 유지하고 거래 등록 시점에 같은 트랜잭션 안에서 같이 갱신(원장은 진실의 원천, 포지션 테이블은 빠른 조회용 파생 캐시).
**부하**: 개인 투자자 기준 거래 건수 자체는 적어서(종목당 수십 건 수준) 이력 조회 자체는 가볍지만, 위 설계 결정들을 먼저 안 하면 나중에 데이터 마이그레이션이 훨씬 아파짐 — 이 프로젝트에서 포트폴리오를 더 키울 계획이면 다른 것보다 먼저 하는 걸 권함.

## 스크리너/발굴

### 13. S&P500 유니버스 스크리너
**원칙**: 실시간으로 조회 시점에 계산하는 게 아니라, 시장폭·섹터로테이션·Put/Call비율(SPY)과 똑같이 **하루 1회 배치가 미리 다 계산해서 스냅샷을 남기고, 화면은 그 스냅샷만 읽는다** — 이번 세션 내내 써온 패턴을 503개 규모로 확장하는 것뿐, 새로운 아이디어는 아님.

**저장 설계를 두 갈래로 분리**:
- `symbol_profiles`(기존, 종목 상세페이지용)는 원본 yfinance 응답 전체를 JSON 블롭 하나로 캐싱하는 구조라, PER·시가총액·배당수익률 같은 걸로 필터링/정렬하려면 매번 JSON을 파싱해야 해서 스크리너용으론 비효율적 — **손대지 않고 그대로 둠**.
- 스크리너 전용으로 **새 테이블**을 하나 둬서, 필터/정렬에 실제로 쓰는 필드(티커, 섹터, 업종, 시가총액, PER trailing/forward, 배당수익률, 베타 등)를 JSON이 아니라 **일반 컬럼**으로 저장 — 그래야 `WHERE sector = ? AND market_cap BETWEEN ? AND ?` 같은 쿼리에 인덱스를 정상적으로 태울 수 있음.

**배치 설계**: 이미 있는 `sp500_batch_loop`(yfinance 호출 속도 조절하며 503종목을 순차로 도는 잡)와 **같은 순회에서 yfinance 응답 하나로 두 곳을 동시에 채움** — 원본 JSON은 `symbol_profiles`에, 추출한 스크리닝 필드는 신규 테이블에. yfinance 호출 횟수가 늘어나지 않음(이미 하던 순회에 저장 대상만 하나 더 추가).

**성능/부하**: 배치가 다 채워둔 뒤엔 신규 테이블 위에서 인덱스 탄 필터/정렬 쿼리 1번 — 503행 규모면 100ms는커녕 그보다 훨씬 빠름, 요청 시점엔 yfinance 호출이 단 한 번도 일어나지 않음. 부하는 전부 "배치가 하루에 503번 도는 속도"에 달려있고, 여긴 반드시 기존 `sp500_batch_loop`의 속도 제한을 그대로 따라야 함(안 그러면 yfinance rate limit — 이미 이 프로젝트가 겪어본 문제).
**신선도**: 하루 1회 배치라 "장중 실시간 PER" 같은 건 아니고 전일 기준 스냅샷 — 스크리너 성격상(펀더멘털은 하루 만에 잘 안 바뀜) 문제 없음.
**안정성**: 특정 종목만 그날 배치에서 실패해도(yfinance 일시 오류 등) 그 종목만 이전 스냅샷을 유지, 전체 배치가 중단되지 않도록 종목별로 개별 예외처리(인디케이터 배치가 심볼별로 실패를 격리하는 것과 동일한 패턴).

### 14. 실적 발표 캘린더
**스코프 결정**: 워치리스트/포트폴리오처럼 **작은 N**(사용자가 실제로 보는 종목)에 한정하면 기존 `SymbolProfileService`와 같은 지연 캐시 패턴(다만 TTL은 24시간 정도로 짧게 — 실적일이 정정되는 경우가 있어서)으로 충분. "S&P500 전체 실적 캘린더"까지 가면 13번과 같은 선행 배치 인프라가 또 필요해지므로, 처음엔 워치리스트/포트폴리오 스코프로 시작하는 걸 권함.
**안정성**: yfinance의 실적일 데이터는 부정확한 경우가 커뮤니티에 종종 보고됨 — "참고용, 부정확할 수 있음" 문구 필수(이번 세션 옵션 지지/저항 패널에 이미 쓴 것과 같은 톤).

## 알림 고도화

### 15. 브라우저 푸시 알림
가격 알림뿐 아니라 7번(크로스)·14번(실적 임박)·16번(거래량 급증) 등 여러 알림 종류가 공유할 **배송 채널** 성격의 인프라라 특정 기능 하나에 종속시키지 말고 독립적으로 설계.
**설계**: 브라우저 Push 구독 정보(엔드포인트+키) 저장 테이블 신규 필요, 서버에서 Web Push 표준으로 암호화 발송.
**안정성/부하 핵심 포인트**: 사용자가 브라우저 알림 권한을 껐거나 오래돼 만료된 구독으로 계속 발송을 시도하면 실패가 쌓임 — 발송 실패(410/404류) 시 **그 구독을 즉시 삭제**하고 재시도하지 않는 처리가 필수(안 하면 죽은 구독에 계속 헛발송하며 리소스만 낭비).
**우선순위**: 알림 트리거 종류가 가격 알림 하나뿐인 지금은 급하지 않음 — 7번(크로스 알림) 정도가 추가된 뒤 같이 가는 게 투자 대비 효율적.

### 16. 거래량 급증 스캐너
**데이터 흐름**: 2번·7번과 완전히 같은 설계 원칙 — **종목별 개별 쿼리 절대 금지, 벌크 IN절 쿼리 1번**(N일 평균 거래량과 최신 거래량을 한 번에 비교). 이번 세션에 증명된 패턴 그대로 재사용.
**스코프 분리**: 실시간 추적 종목(13~50개)은 장중 급등 감지가 의미 있지만, S&P500 전체(분봉 없음)는 "오늘 거래량 vs N일 평균"을 하루 1회 배치로만 볼 수 있음 — 두 스코프를 다른 기능처럼 명확히 나눠서 설계.
**성능/부하**: 실시간 추적분은 기존 실시간 파이프라인에 얹거나 5분 배치 확장, 전체 유니버스분은 시장폭·섹터로테이션과 같은 1일 1회 배치 시간대(07시대)에 묶어서 실행.

### 17. 경제지표 캘린더(FOMC/CPI 등)
**설계 전 단계 — 소스 조사가 먼저 필요**: 이번 세션에 옵션 OI 문제를 풀 때처럼, "무료로 신뢰할 수 있는 소스가 실제로 있는가"부터 확인해야 함(이 문서에서 바로 설계를 확정하기엔 이름 붙일 데이터 소스가 아직 없음). 후보를 찾으면 CBOE 검증 때처럼 실제 응답을 까보고 rate limit/이용약관까지 확인한 뒤에 설계를 잡는 걸 권함 — 원하시면 이 조사부터 먼저 진행하겠습니다.

### 18. 해외주식 원화환산 손익
**데이터 흐름**: `USDKRW`이 이미 `market_index_history_snapshot`에 일봉으로 있음 — 포트폴리오 응답에 최신 종가 환율만 곱해서 표시. 신규 캐싱 불필요(기존 서비스에 "최신 종가 1개" 조회 메서드만 추가).
**성능/부하**: 이미 캐시된 값 하나 읽는 수준, 무시할 만함.
**안정성**: 일봉 기준이라 장중 환율 변동은 반영 안 됨 — "전일 종가 환율 기준"임을 명시해서 실시간으로 착각하지 않게.

### 19. 지표 설명 툴팁
순수 프론트엔드 정적 콘텐츠 — 백엔드/성능/부하 고려사항 없음. 다른 항목과 독립적으로 아무 때나 진행 가능.

## 종합 메모
- **부하 관점에서 가장 조심해야 할 항목은 4번**(이력 적재) — 스냅샷 단위를 "티커당 최신 1행"에서 "티커당 날짜당 1행"으로만 바꿔도 무한 성장을 막을 수 있음. 이 설계 없이 이력 적재부터 하면 나중에 큰 리팩터가 필요해짐.
- **가장 위험한 숨은 전제조건은 13번**(스크리너) — 화면 자체는 가벼운데, 그걸 뒷받침할 "전체 유니버스 프로필 사전 채우기 배치"가 없으면 최악의 경우 요청 한 번에 yfinance 500번을 부르게 됨. 14·16번의 "전체 유니버스" 버전도 같은 함정.
- **가장 반복되는 설계 원칙**: 차트 오버레이류(MACD/볼린저/OBV/스윙 고저)는 **클라이언트 계산**이 정답이고, 스캔/알림/스크리닝처럼 "화면 안 봐도 동작해야 하는" 것만 서버 계산+저장이 필요. 이 구분을 안 하면 오버레이 지표까지 전부 서버에 태워서 불필요한 배치 부하가 생김.
- **가장 규모가 큰 결정 필요 항목은 12번** — 코드 이전에 FIFO/평균단가 중 계산 방식부터 정해야 함.
- **"실시간 계산 vs 배치+캐싱" 질문의 기본 답은 항상 배치+캐싱**: 이 문서의 "N개 심볼을 다루는 기능"(2·4·13·14·16의 전체유니버스판)은 전부 같은 결론 — 요청이 올 때 계산하지 않고, 하루 단위(또는 필요시 더 촘촘한 주기)로 미리 계산해서 MySQL 스냅샷에 남기고, 요청은 그 스냅샷만 읽는다. 이번 세션에 시장폭/섹터로테이션/Put-Call비율(SPY)에서 이미 쓴 패턴이고, 13번(스크리너)도 규모만 503개로 커질 뿐 원칙은 동일.
