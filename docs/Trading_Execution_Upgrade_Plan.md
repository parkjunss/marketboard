## General — 목적과 방향

Marketboard의 시세 조회·ETF 연구·일봉 모의 운용을 기반으로, 주문 실행의 정확성과 장애 복구를 설명할 수 있는 포트폴리오를 만든다. 핵심 결과물은 사용자가 장애를 재현하고 주문·체결·잔고의 변화를 검토할 수 있는 모의 실행 검증실이다.

공고는 Python 비동기 개발, REST/WebSocket 처리, 전략 검증, 리스크 관리와 함께 동시성·순서 결정론, 재진입 상태 관리, 일관된 가격 기준을 필수 검증 항목으로 요구한다. 설계·개발·운영 총괄 포지션이므로 프로젝트의 완성도와 실제 프로덕션 운용 경력을 구분한다.

### 현재 기반과 차이

| 요구 | 확인한 기반 | 추가로 증명할 내용 |
|---|---|---|
| Python 비동기·실시간 처리 | `collector/app/finnhub_source.py`의 asyncio/WebSocket 재연결, `collector/main.py`의 비동기 작업 | 중복·지연·역순 이벤트, 데이터 공백과 재연결 복구 |
| 백테스트·전략 검증 | `collector/app/etf_backtest.py`의 비용 반영, `etf_workflow.py`의 입력 데이터 보존 | 실행 엔진과 연결된 재현 가능한 검증 |
| 모의 운용 | `etf_workflow.py`의 완료 일봉 기반 평가·거래, `EtfPaperService.java`의 상태·스냅샷 저장 | 주문 승인·부분 체결·취소·응답 불명 상태 |
| 중복 방지·동시성 | 기존 API 멱등성, 모의 계좌의 DB 행 잠금 | 거래소 주문 식별자·체결 중복 제거·복구 후 원장 일치 |
| 모니터링 | `observability/`의 Prometheus·Grafana 구성 | 거래 실행 지표·알림 규칙·복구 절차의 실제 검증 |

기존 테스트에는 모의 평가 반복 호출, 입력 보존, 수집기 장애 시 상태 유지 등의 사례가 있다. 이것만으로 외부 주문의 멱등성이나 다중 프로세스 복구가 검증되었다고 주장하지 않는다.

### 구조 원칙

- Python: 전략 판단, 주문 상태 전이, 포지션·리스크 계산, 모의 거래소 처리의 권위 있는 구현.
- Spring: 사용자 인증·권한, 실행 요청 API, 영속화 경계와 조회 API. 동일 계산을 Java나 브라우저에 중복 구현하지 않는다.
- Next.js: 실행 설정, 상태·근거 표시, 장애 시나리오 실행과 결과 비교.
- 기존 일봉 모의 운용과 새 주문 실행 계정은 분리한다. 기존 기록을 새 체결 원장으로 간주하거나 자동 변환하지 않는다.
- 주문 실행 상태의 단일 쓰기 주체와 DB 트랜잭션 경계는 구현 전에 ADR로 확정한다. Python과 Spring이 동일 상태를 각각 갱신하지 않는다.
- 첫 버전은 단일 계좌·단일 전략·모의 거래소로 제한한다. Kafka, 새 시계열 DB, 다중 거래소는 측정된 필요가 생겼을 때 검토한다.

## Spec — 단계별 구현과 완료 기준

### 0단계: 도메인·계약 확정

산출물: 상태 전이표, 이벤트 스키마, 가격 정의, 저장소와 API 계약, 영속화 ADR.

- 주문과 포지션의 상태 머신을 구분한다. 주문은 생성·제출 중·접수·부분 체결·완료·취소·거절·결과 불명 등을 모델링한다. 타임아웃을 주문 실패로 단정하지 않는다.
- 재진입 금지의 범위(계좌·전략·종목), 해제 조건, 거래일·시간대 기준을 명시한다.
- 신호 가격, 주문 기준가, 체결가, 수수료 반영 평균단가, 평가 가격, 손절 기준가를 구분한다.
- 금액·수량은 Decimal 및 DB DECIMAL을 사용하고 호가·수량 단위와 반올림 정책을 정한다. 기존 연구용 float 계산의 전면 변경은 별도 과제로 둔다.
- 결정론의 범위를 정의한다. 같은 이벤트 집합·전략 버전·설정·정규화된 순서에서 경제적 결과가 같아야 한다. 실제 발생 순서가 달라져 전략 판단이 바뀌는 경우까지 같은 결과라고 주장하지 않는다.
- 수신 원본 로그는 관측 순서를 보존하고, 경제적 상태를 재현하는 처리 로그는 안정된 이벤트 순서와 식별자를 사용한다. 수신 시각 등 비결정적 메타데이터는 비교 대상에서 명시적으로 제외한다.

완료 기준: 부분 체결 후 취소, 타임아웃 후 체결 확인, 청산 후 재진입 차단을 전이표로 설명할 수 있다.

### 1단계: 최소 주문 실행 엔진 — P0

- 모의 거래소 어댑터와 단일 전략을 연결한다.
- 주문 식별자와 체결 식별자를 저장하고 중복 이벤트를 제거한다.
- 주문 생성 시 자금을 예약하고 부분 체결·취소 시 예약 잔액을 정확히 반영한다.
- 이벤트 기록·상태·잔고 갱신의 원자성을 확보하고 계좌 단위 처리 순서를 통제한다.
- 제출 의도를 영속화한 뒤 외부 어댑터를 호출한다. 외부 호출과 DB 저장 사이 장애는 원자적이라고 가정하지 않고 대사로 복구한다.
- 최대 주문 금액·종목 비중·데이터 신선도 검사를 주문 전 적용한다. 자금 부족과 잘못된 가격은 명시적 사유로 차단한다.

완료 기준: 정상 체결·부분 체결·취소·거절 테스트가 통과하고 현금·수량 보존 및 중복 체결 미반영을 검증한다. 수수료와 손익을 포함한 원장 등식으로 검증한다.

### 2단계: 장애 재현과 리플레이 — P0

| 시나리오 | 기대 결과 |
|---|---|
| 동일 요청·체결 알림 반복 | 주문·잔고 변화가 중복 발생하지 않음 |
| 부분 체결 후 취소 | 체결분 유지, 미체결 예약분 해제 |
| 주문 제출 응답 유실 | 결과 불명으로 유지하고 식별자로 조회·대사; 무조건 재주문하지 않음 |
| 체결 알림 역순·지연 | 시퀀스·누적 체결량 정책에 따라 수렴하거나 명시적 대기·대사 상태 진입 |
| 제출 직후·체결 저장 중 재시작 | 영속 기록으로 복구하고 외부 주문과 대사 |
| 시세 단절·오래된 가격 | 신규 진입 차단, 상태·차단 이유 표시 |
| 동일 이벤트를 여러 작업자가 처리 | DB 제약과 직렬화 정책으로 단일 반영 |
| 청산 직후 신규 신호 | 저장된 재진입 금지 정책 적용 |

완료 기준: 고정 입력·버전·시드의 반복 실행에서 포지션·잔고·경제적 처리 기록이 일치한다. 실제 DB를 사용하는 동시성·프로세스 재시작 테스트를 포함한다. mock 테스트만으로 복구를 입증하지 않는다.

### 3단계: 검증실 화면과 운영 통제 — P1

2026-10-20 구현: 실행 상태·타임라인·전체 상태 리플레이 차이, 영속 장애/복구 알림, 종류별 활성 알림 지표, 공개 읽기 전용 예제를 추가했다. 로컬 브라우저에서 계산 서버 장애 및 Python/Java 재시작 후 복구를 확인하고, 별도 MySQL 8.0.45에서 실행 서비스 테스트 9개를 통과했다. 전체 Flyway 업그레이드·운영 배포 검증은 남아 있다. 상세 근거: [P1 검증 기록](Execution_P1_Verification.md).

- 실행 생성 → 실행 상세 → 장애 주입 → 복구·리플레이 비교의 흐름을 제공한다.
- 주문 타임라인에 전이 사유, 기준 가격, 리스크 판단, 체결 내역을 표시한다.
- 실행 중지는 신규 주문 차단과 기존 주문 취소 요청을 구분한다. 중지 버튼이 기존 포지션을 자동 청산한다고 가정하지 않는다.
- 데이터 지연, 결과 불명 주문 수·지속 시간, 대사 불일치, 처리 실패, 리스크 차단을 관측한다.
- 알림 조건·해제 조건·중복 억제와 복구 절차를 문서화한다.
- 실행 데이터 소유권을 API에서 검증한다. 장애 주입은 격리된 모의 실행에만 허용한다.

완료 기준: 브라우저에서 정상·실패·재시작 흐름을 확인하고, 다른 사용자의 실행 접근 차단과 중지 후 신규 주문 차단을 검증한다. 알림은 의도적으로 장애를 발생시켜 전달·복구까지 확인한다.

### 4단계: 자체 모의 운용 기록과 지원 자료 — P2

2026-10-20 사용자 결정: 실제 증권사 API를 연결하지 않는다. 자체 시뮬레이터로 주문·체결·장애를 재현하고 계좌별 기록을 저장한다.

구현·검증 완료 범위와 실행 방법은 [자체 모의 운영 기록](Execution_Simulation_Operations.md)에 정리했다. 실제 로그인·MySQL 8.4·Redis·독립 모의 서버의 통합 흐름, 재시작 후 기록 보존, 지속 경보 발생 및 복구를 확인했다.

후속 구현: [자동 모의 매매](Auto_Trading_Spec.md)의 전략 설정, 과거 가격 자동 진행, 매매 일지, 일시정지·재개·종료를 연결했다. [검증 기록](Auto_Trading_Verification.md)에 자동 테스트 및 브라우저 장애·복구 증거를 정리했다.

- 독립 Python 모의 실행 진입점으로 외부 시세 수집 없이 운용한다.
- 실제 인증·MySQL에 실행 설정, 명령, 잔고, 장애·복구 이력을 저장하고 재접속 후 조회·재생한다.
- 운영 대시보드에서 지속되는 모의 실행 장애를 식별한다.
- 포트폴리오에 아키텍처, 장애 사례, 재현 방법, 검증 결과와 제한을 묶는다.
- 합성 가격 기반 결과이며 실제 투자 수익률이나 브로커 연동 실적으로 표현하지 않는다.

## 검증 증거와 이력서 연결

| 증거 | 담을 내용 |
|---|---|
| 재현 가능한 실행 | 입력·전략 버전·설정·시드·실행 ID |
| 테스트 결과 | 실행 명령·환경·커밋·성공/실패·제외한 항목 |
| 장애 분석 | 발생 지점, 잘못될 수 있는 상태, 방지·복구 방식 |
| 화면 | 부분 체결, 결과 불명 주문 대사, 리플레이 비교 |
| 성능 | 고정 부하 조건에서 처리량·지연·오류율 측정; 측정 전 목표 수치를 실적으로 쓰지 않음 |

구현·검증 후 사용할 수 있는 이력서 문장 예시:

> 부분 체결·중복 이벤트·주문 타임아웃을 재현하는 모의 실행 환경을 구축하고, 장애 복구 전후의 포지션·잔고 일치 여부를 자동 검증했습니다.

현재 단계에서는 위 문장을 완료 실적으로 쓰지 않는다. 실서비스 운용, 실제 거래소 연동, 부하 수치는 각 증거가 확보된 범위만 기술한다.

## 착수 순서와 일정 산정

의존 순서: 0단계 계약 확정 → 1단계 최소 엔진 → 2단계 장애 검증 → 3단계 화면·운영 → 4단계 자체 모의 운용 기록.

첫 구현 단위는 ‘모의 주문 하나의 생성 → 부분 체결 → 취소 → 잔고 확인’으로 잡는다. 이 수직 기능에 DB·Python·Spring API·화면·통합 테스트를 연결한 뒤 장애 종류를 늘린다. 0단계에서 저장소 경계와 기존 코드 재사용 범위를 확정한 후 작업량을 산정한다. 지원 마감일과 주당 투입 시간이 정해지기 전에는 확정 일정을 제시하지 않는다.

이번 검토에서 발견한 기존 수정 파일(`compose.local.yml`, `frontend/Dockerfile`, `frontend/src/components/news/news-list.module.css`, `frontend/src/lib/api.ts`)은 본 계획의 구현 범위로 간주하지 않으며 수정하지 않았다.
