# MarketBoard — 업그레이드 아이디어

> 작성: 2026-07-19
> 목적: `stock-monitor-dev-plan.html`의 Phase 1~7 로드맵은 전부 완료되고 실제 배포(`https://marketboard.duckdns.org`)까지 끝난 시점에서, 다음에 시도해볼 만한 개선 방향을 정리. 실행 계획이 아니라 후보 목록 — 실제로 진행할 항목은 그때그때 골라서 별도로 계획을 짤 것.

각 항목에 `[체감난이도: S/M/L]`을 붙여둠. S=몇 시간~반나절, M=1~2일, L=며칠 이상(설계 필요).

## 바로 해볼 만한 것 (임팩트 대비 비용이 낮음)

1. **관리자/공개 API rate limit 적용** `[S~M]` — 계획서 §08 운영 유의사항에 "관리자 API는 rate limit 적용"이라고 처음부터 명시돼 있었는데 실제로는 아직 아무 데도 없음(`RateLimit`/`Bucket4j`/`resilience4j` 코드베이스에 전무). 이제 진짜 인터넷에 공개돼 있으니(`marketboard.duckdns.org`) 로그인/회원가입 엔드포인트부터 브루트포스 방어용으로 우선 적용할 가치가 있음. Spring이면 `bucket4j-spring-boot-starter`가 제일 간단.
2. **`npm audit` 무디레이트 취약점 2건 정리** `[S]` — `postcss`(Next.js 번들 의존성) XSS 관련. `npm audit fix --force`가 제안하는 Next.js 9.x로의 다운그레이드는 명백히 잘못된 해법(현재 16.x에서 대퇴보) — Next.js 자체 업데이트로 postcss가 같이 올라가는지 확인하거나, 실제 영향받는 코드 경로가 있는지부터 확인.
3. **DB 백업 cron** `[S]` — 계획서 운영 유의사항에 "MySQL 덤프 cron(일 1회)"이 있었는데 아직 없음. Pi의 `mysql-data` 볼륨이 유일한 데이터 저장소라 Pi가 죽거나 볼륨이 깨지면 전부 날아감. `docker exec marketboard-mysql mysqldump ...`를 cron이나 별도 backup 컨테이너로 하루 1회, 외부(예: 다른 디스크/클라우드)로 보내는 정도만 해도 충분.
4. **`AMZN` 테스트 잔재 + 방금 만든 `e2e-check-*` 테스트 계정 정리** `[S]` — 둘 다 기능엔 지장 없지만, 관리자 화면 데이터가 깔끔해짐.

## 제품 기능

- **포트폴리오를 스냅샷이 아니라 거래 이력(매수/매도 로그)으로 확장** `[L]` — 현재 `portfolio_positions`는 수량/평단가 스냅샷만 저장하고 개별 매매 기록이 없음(PROGRESS.md에 이미 "거래 이력 아님"으로 명시돼 있음). 실현손익, 기간별 수익률 추이, 배당 기록까지 하려면 `transactions`류 테이블이 필요 — 지금 스키마로는 못 함. 포트폴리오 기능을 더 키우고 싶다면 이게 선행돼야 함.
- **대시보드 위젯 커스터마이즈 UI** `[M]` — `dashboard_configs` 테이블 + 백엔드 CRUD(`DashboardConfigController` 등)는 이미 있는데, 프론트 `/dashboard` 페이지(129줄)는 고정 레이아웃만 렌더링하고 있어서 이 기능이 사실상 안 쓰이고 있음. 드래그 배치까지는 아니어도 "패널 켜고 끄기" 정도만 프론트에 붙여도 이미 있는 백엔드를 실제로 활용하게 됨.
- **S&P500 유니버스 스크리너** `[M]` — 503종목 데이터(가격/재무)가 이미 배치로 수집되고 있는데(`in_sp500_universe`), 현재는 실시간 대상 13종목 외엔 조회 API만 있고 화면에서 "전체 유니버스를 필터/정렬해서 훑어보는" 기능이 없음. PER/시가총액/섹터 등으로 필터링하는 스크리너 페이지를 만들면 이미 모아둔 데이터를 제일 잘 써먹는 기능이 될 것.
- **추가 기술지표(MACD/볼린저밴드/EMA)** `[M]` — 현재 SMA20/SMA50/RSI14만 있음. `TechnicalIndicators.java` 확장 + `indicators` 테이블 컬럼 추가로 비교적 안전하게 늘릴 수 있음.
- **브라우저 푸시 알림** `[M]` — 가격 알림이 지금은 인앱 토스트뿐이라 탭을 안 열고 있으면 못 봄. Web Push API + 백엔드에서 알림 트리거 시 푸시 발송 추가하면 실사용성이 크게 오름.
- **다크 모드** `[S~M]` — Astryx 디자인 시스템이 테마 지원을 전제로 하는 걸로 보이니(`astryx theme`), 이미 있는 토큰 체계를 활용하면 큰 리팩터 없이 가능할 수 있음.
- **OAuth 소셜 로그인(Google 등)** `[M]` — 현재 인증은 이메일/비밀번호(JWT) 한 가지뿐(`auth-context.tsx`, `signup`/`login` 페이지). Spring Security의 `spring-boot-starter-oauth2-client` + 프론트 콜백 페이지 추가가 필요하고, 기존 로컬 계정과 OAuth 계정을 같은 이메일로 병합할지(계정 연동) 여부부터 먼저 정해야 함.
- **회원가입 폼 보강: 비밀번호 확인 + 약관 동의 + 이메일 인증** `[S~M]` — 현재 `signup/page.tsx`는 이름/이메일/비밀번호 3개 입력만 받고 바로 가입 처리됨(비밀번호 확인 필드 없음, 약관 동의 체크박스 없음, 이메일 인증 없이 즉시 로그인 가능). 비밀번호 확인은 프론트 검증만으로 충분(`[S]`), 약관 동의는 체크박스 + 약관 텍스트/페이지 필요(`[S]`), 이메일 인증은 인증 토큰 테이블 + 발송 메일 서비스(SMTP or SES 등) + "인증 전엔 로그인 제한" 로직까지 필요해 상대적으로 큼(`[M]`).

## DevOps / 배포

- **리버스 프록시 재구성** `[L]` — 이미 방향 합의됨(사용자 확인: "나중에는 공유 리버스 프록시로"). `tradehub-nginx`가 지금 stop된 채로 남아있는 임시 상태. 인프라 방향에 따라 둘 중 하나만 선택: (A) compose 유지 시 `nginx-proxy` + `acme-companion` 조합으로 두 프로젝트를 Host 헤더 라우팅 하나로 통합, (B) 아래 "쿠버네티스로 전환한다면" 서브섹션의 `ingress-nginx` + `cert-manager`. MarketBoard의 `nginx/` 설정은 이걸 염두에 두고 독립 디렉터리로 짜뒀으니 어느 쪽이든 마이그레이션 자체는 크지 않을 것.
- **무중단 배포** `[M]` — 지금 CI의 `docker compose up -d`는 컨테이너를 교체하는 순간 짧게라도 다운타임이 생김(개인 프로젝트라 지금까진 문제 없었지만, 실사용자가 늘면 체감됨). 위 리버스 프록시 선택과 묶어서 판단할 것 — compose 유지 시 backend에 `healthcheck`+`start_period`를 거는 정도부터, k8s 전환 시 Deployment 기본 rolling update + readinessProbe로 사실상 자동 해결(아래 서브섹션 참고).
- **CI에 E2E 테스트 통합** `[M]` — 지금까지 Playwright E2E는 전부 그때그때 스크래치 디렉터리에서 수동으로 돌린 것(이번 세션 포함, 매번 임시 스크립트). `frontend/e2e/`에 정식으로 넣고 `ci.yml`의 `deploy` job 뒤에 "배포 후 스모크 테스트"로 붙이면, 배포가 실제로 성공했는지(단순히 컨테이너가 떴는지가 아니라 로그인까지 되는지) 자동으로 검증됨.
- **로그 중앙화(Loki 등)** `[M]` — 지금은 각 컨테이너 `docker logs`로만 확인 가능. Prometheus/Grafana는 이미 있으니 Loki+Promtail을 얹으면 로그도 Grafana에서 한번에 볼 수 있음.
- **Grafana 알림 규칙 설정** `[S]` — 대시보드는 있는데 알림(예: 콜렉터 WS 연결 끊김, 인디케이터 실패율 급증)은 아직 설정 안 돼 있어서 사람이 대시보드를 직접 봐야만 이상을 앎.

### 쿠버네티스로 전환한다면

> 배경: 단일 Pi(rasp4) 위 단일 노드 운영이라, k8s 도입의 핵심 이점(HPA, 멀티노드 스케줄링)은 못 누림 — 학습 목적 성격이 크다는 점을 감안하고 접근할 것. 이미지가 이미 CI에서 `ghcr.io`로 push되고 있어서(`.github/workflows/ci.yml`) 매니페스트로 옮기는 자체의 진입장벽은 낮음.

- **k3s 단일 노드 클러스터로 전환** `[L]` — 현재 `docker-compose.yml` 9개 서비스(mysql/redis/backend/collector/frontend/prometheus/grafana/nginx/certbot/duckdns)를 Deployment/Service/ConfigMap/Secret 매니페스트로 재작성. 전체 스택을 한 번에 옮기기보다 무상태 서비스(backend/collector/frontend)부터 먼저 옮기고 mysql/redis는 당분간 compose에 남겨두는 단계적 전환도 가능.
- **`ingress-nginx` + `cert-manager` 도입** `[M]` — 지금 수작업으로 돌아가는 `nginx`/`certbot` 컨테이너 쌍과 `nginx/init-letsencrypt.sh` 부트스트랩을 대체. 위 "리버스 프록시 재구성"의 (B) 경로. tradehub도 같은 ingress에 Host 라우팅으로 합류시킬 수 있음.
- **mysql-data를 PVC로 전환** `[M]` — 지금은 named volume(`mysql-data`). 단일 노드라 k3s 기본 `local-path-provisioner`로 충분, 별도 스토리지 클래스 구축은 불필요.
- **readinessProbe + rolling update** `[S]` — 위 "무중단 배포"의 k8s 경로. Deployment 기본 롤링 업데이트 전략으로 사실상 자동 해결(별도 블루/그린 설계 불필요).
- **CI 배포 스텝 교체** `[S~M]` — self-hosted 러너가 이미 Pi 위에서 도는 구조라(`ci.yml` deploy job), 이미지 build/push 스텝은 그대로 두고 마지막 `docker compose up -d`만 `kubectl apply -k` 또는 `helm upgrade`로 바꾸면 됨. SSH 원격 배포로 바꿀 필요는 없음.
- **관측 스택 재검토** `[M]` — 지금처럼 Prometheus/Grafana를 직접 컨테이너로 둘지, `kube-prometheus-stack` Helm 차트로 옮길지 결정 필요. 개인 규모에선 전자를 유지하는 것도 합리적 선택.

## 실전 투자용 신뢰도 강화

> 배경: 인프라를 아무리 고도화해도, 무료 티어 API + 개인 서버 하나로 서빙하는 시세를 실제 매매 판단에 쓰려면 결국 "이 데이터를 얼마나 믿을 수 있는가"가 병목. 아래는 그 신뢰도를 올리는 방향 — 우선순위 순. 보안 섹션의 2FA/감사 로그/레이트리밋도 개인 자산 데이터가 걸리는 만큼 이 트랙과 함께 우선순위가 올라감(별도 항목 아님, 보안 섹션 참고).

1. **포트폴리오를 거래 이력으로 확장** `[L]` — 제품 기능 섹션과 동일 항목. 실현손익/기간 수익률 계산 자체가 지금 스키마(스냅샷)로는 불가능해서, 실전 활용을 노린다면 이게 선행돼야 함.
2. **데이터 신선도 · 연결 상태 표시** `[S~M]` — 지금은 콜렉터 WS 연결이 끊겨도 화면엔 티가 안 남. 마지막 갱신 시각, 실시간/폴백(REST) 여부를 UI에 노출해서 "오래된 가격을 최신인 줄 알고" 판단하는 상황을 막을 것.
3. **포트폴리오 리스크 지표** `[M]` — 변동성, 최대낙폭(MDD), 섹터/종목 집중도, 샤프비율 등. 단순 시세 조회를 넘어서는 의사결정 도구가 되려면 필요. `TechnicalIndicators.java` 확장(제품 기능 섹션)과 별개로 포지션 단위 계산이라 `PortfolioService` 쪽에 새로 붙여야 함.
4. **규칙 기반 알림 고도화** `[M]` — 현재 가격 임계값 알림뿐. RSI 과매수/과매도, 이동평균 골든/데드크로스 등으로 확장하면 "브라우저 푸시 알림"(제품 기능 섹션) 항목과 묶어서 진행하기 좋음.
5. **데이터 라이선스/지연 재확인** `[S]` — Finnhub 무료 티어의 실시간성·재배포 제약을 다시 확인. 기술 이슈가 아니라 법적/신뢰성 이슈라 별도로 짚어야 하고, 화면에 "본 데이터는 투자 참고용이며 지연될 수 있음" 같은 고지가 필요할 수도 있음.
